# 店舗・役職・権限

## 参照関係

- `mst_users`: 本人情報・認証・`is_system_admin`（bool、初期値 false）。
- `t_store_users`: 店舗所属。`access_role_id` → `mst_access_roles`、`role_id` → `mst_roles`。
- `mst_access_roles`: `cast` / `staff` の区分。管理者は登録しない。
- `mst_roles`: 店舗内の役職。`access_role_id` → `mst_access_roles`。所属とは `(role_id, store_id, access_role_id)` の複合外部キーで一致させる。
- `mst_permissions` / `t_role_permissions`: 役職が使える機能を定義する。

## 認可と店舗選択

`GET /api/user` は本人の公開情報、LINE連携済みか、全有効所属、選択可能な店舗、選択中の店舗・所属、利用可能な権限、ホーム画面を返す。パスワード・LINE ID・旧権限カラムは返さない。

`POST /api/user/active-store` に `store_id` を渡すと、利用可能な店舗に限りセッションの店舗を切り替える。初回は最初の有効店舗を選ぶ。選択済み店舗の所属が失効した場合は別店舗へ自動切り替えせず、権限をなくす。

退店済みの所属、論理削除済みの店舗・組織は除外する。削除済み役職の所属自体は表示するが、役職とその権限は返さない。権限はHTTPリクエストごとにDBから検証する。フロントのメニューとAPIの認可は同じpermissionを使う。

| permission | 機能 |
| --- | --- |
| shift.submit | 自分のシフト提出・下書き・確定シフト確認 |
| shift.manage | 提出依頼・提出状況・代理編集・編成・確定・LINE再通知 |
| shift_calendar.view | 店舗全体の出勤カレンダー閲覧。編集・確定は含まない |
| cast.manage | 所属店舗のキャスト一覧・退職登録・在籍への復帰 |

System管理者は有効な全店舗を選択でき、選択した店舗で全4権限を持つ。店舗がない場合はマイページに移動する。キャスト区分の有効所属は、役職がなくても自分のシフト提出・確認（shift.submit）を基本機能として持つ。追加の閲覧・管理権限は役職から取得する。スタッフは役職に明示的に付与された権限を持つ。

`mst_users.auth_type / user_type / role_type` はDB互換性のため残しているが、機能の認可・フロント表示・キャスト抽出には使わない。

## シフトの店舗分離

`t_shift_requests.store_id` で店舗を特定し、子のシフト・日別決定・割り当ても依頼を通じて店舗を特定する。一覧、公開シフト、対象キャスト、LINE通知はその店舗に限定する。別店舗の依頼IDを指定した操作は404とする。フロントが送る `X-Store-Id` とセッションの店舗が違う場合は409として再読み込みを促す。

旧依頼のstore_idは推測して設定しない。NULLの旧依頼は全店舗で非公開。必要な場合は正しい所属先を明示的に移行する。LINEジョブにも店舗IDを保存し、実行時に在籍を再検証する。店舗IDを持たない旧ジョブは送信しない。

## 開発データ

開発中のDBは `php artisan migrate:fresh --seed` で再作成する前提（既存データは消去される）。この変更作業では実行していない。

DatabaseSeeder は「株式会社にし山」「clab にし山」、ママ・Manager・Staff・キャスト役職、開発用2ユーザーの所属を作成する。

| 役職 | 区分 | 権限 |
| --- | --- | --- |
| ママ | cast | shift.submit / shift_calendar.view |
| Manager | staff | shift.manage / shift_calendar.view / cast.manage |
| Staff | staff | shift_calendar.view |
| キャスト | cast | shift.submit |

`nishioka@example.com` はManager、`ayana@example.com` はキャスト役職。固定ULIDとコードにより再実行しても重複させず、店舗・役職の名称と論理削除、所属の変更は保持する。初期権限の紐付けはSeeder再実行時に再付与する。System管理者は自動付与しない。

マイグレーションのdownは外部キー依存の逆順に実行する。

## キャスト管理

ManagerとSystem管理者はヘッダーメニューの「キャスト管理」から選択店舗の在籍・退職キャストを確認できる。在籍状況の絞り込みと氏名・ログインID検索に対応する。

`GET /api/admin/casts` は同店舗のキャスト所属のみを返す。`PATCH /api/admin/casts/{membershipId}/employment` に `retired: true/false` を渡すと `t_store_users.deleted_at` を更新する。いずれも `cast.manage` が必須。別店舗の所属・スタッフ所属・削除済みユーザーの更新は404。

退職は店舗所属だけのsoft deleteであり、mst_usersやシフト履歴は削除しない。他店舗の所属も維持する。退職済み所属は店舗の利用権限・シフト候補・LINE通知対象から除外される。在籍復帰は同じ所属を復元し、元の役職を保持する。元の役職が削除済みなら権限は復活しない。重複した退職登録で初回の退職登録日時は変更しない。

## キャスト招待QR

キャスト管理メニューを「キャスト一覧」「キャスト追加」に分ける。追加画面は選択中店舗のULIDを店舗コードとして表示し、期限付きトークンを含む `/login?store=...&invite=...` をQRにする。QRはフロント内で生成し、外部QR生成サービスには送信しない。

`GET /api/admin/casts/invitation` は選択店舗の現在の招待情報を返す（未発行・期限切れはurl=null）。`POST /api/admin/casts/invitation` はcast.manageとCSRFを検証して発行・再発行する。再発行時は同店舗の旧トークンを即時無効化する。`GET /api/cast-invitations/resolve` はトークンと有効店舗・組織を確認し、ログイン画面用の店舗名とコードのみを返す。トークンはランダム64文字で、t_cast_invitationsにSHA-256ハッシュと再表示用の暗号化トークン、UTCの発行・失効日時を保存する。store_idは主キーのため有効な招待は店舗ごとに1つ。発行から15分後ちょうどに失効する。店舗のULIDは変更しない。

LINE認証開始時に招待情報をstate/nonce/PKCEと同じサーバーセッションに保持する。コールバックのqueryから登録店舗・区分・役職・権限を受け取らず、LINE本人情報の検証後にサーバー側の招待情報を使う。ユーザー作成と所属登録は同一トランザクションで行い、所属は cast / role_id=NULL / 基本権限shift.submitとする。

既存LINEユーザーは同じ本人アカウントを再利用する。他店舗の所属、既存の役職、System管理者フラグを変更しない。同店舗の有効所属があれば重複登録しない。退職済み所属は招待で復帰させずManagerの在籍復帰操作を必要とする。削除済みアカウントも自動復帰させない。

登録後は招待店舗を選択中店舗としてマイページへ移動する。登録直後から自分のシフト提出・確定シフト確認を利用できる。店舗全体の閲覧・管理は許可されない。通常ログイン・既存LINE連携には招待登録を適用しない。

QRのURLは FRONTEND_URL を基準にする。スマートフォンからアクセスできる公開URLを設定し、既存のLINEコールバックURL設定をその配信環境に合わせる。


LINE認証開始時とコールバックの所属登録時の両方で招待の失効・再発行を検証する。認証中に期限が切れたり再発行された場合も登録しない。追加画面は日本時間の有効期限と残り時間を表示し、失効時はQRとURLを非表示にする。ページを開くだけでは発行しない。

## LINE友だち追加

認可URLに `bot_prompt=aggressive` を付け、認証の同意後に公式アカウントの友だち追加案内を出す。LINE Developersでログインチャネルと通知ボットの公式アカウントをリンクする必要がある。双方が同じプロバイダー配下にあり、設定者が両方の管理者であること。

`LINE_OFFICIAL_ACCOUNT_ID`（@から始まるベーシックID）を設定すると、マイページに通知ボットの友だち追加ボタンも表示する。実環境の通知ボットは @949bhgpp（aster. シフト通知）。リンクによる友だち追加はチャネル紐付けの有無にかかわらず利用できる。追加済みとは推測せず、未追加・ブロック中のユーザーの状態も自動変更しない。

## キャストの役職設定

キャスト管理権限 cast.manage を持つManagerとSystem管理者は、一覧の「役職を設定」から役職を変更・解除できる。GET /api/admin/casts は対象キャストと、選択店舗内の有効なキャスト用役職・permission名を返す。

PATCH /api/admin/casts/{membershipId}/role に role_id（整数またはnull）を渡すと、対象所属のrole_idのみを変更する。役職は同じ店舗・同じキャスト区分・未削除でなければ422。別店舗・スタッフ所属・削除済みユーザーは404。認可と選択店舗の検証は既存のキャスト管理と共通。

役職なしでもキャスト基本機能 shift.submit は維持する。追加権限は次のHTTPリクエストから反映する。退職済み所属も役職変更できるが、在籍に戻すまでは権限を持たない。他店舗の所属・在籍状態・usersのSystem管理者フラグは変更しない。

## ログインIDの採番

ログインIDは最初の有効な店舗所属が作成されたとき、`店舗ID（最低2桁） + access_role_id（最低2桁） + A + mst_users.id（最低4桁）` で発行する。ゼロ埋めだけを行い、桁を切り詰めない。例：店舗1・access_role_id=1・users.id=23 は `0101A0023`。users.id=10000 は末尾 `A10000` のままで、Bには繰り上げない。

ユーザーIDはDBのauto incrementで確定した値を使い、MAX(id)+1や区分別連番テーブルでは採番しない。新規スキーマには login_id_sequences を作成しない。既存環境に残っていても読み書きしない。

招待登録と開発用ユーザーの所属作成時に一度だけ発行する。発行済みIDは他店舗への所属、役職変更、再入店、Seeder再実行で変更しない。既存の旧形式ログインIDも保持し、ログイン時は旧形式・新形式をともに受け付ける。所属未登録のユーザーはlogin_id=NULLで、LINEでログインできる。

login_idはnullable・64文字・unique。既存環境には 2026_10_25_030000 のマイグレーションで列を拡張する。down()でも既に発行した長いIDや未所属ユーザーのNULLを失わないよう列を狭めない。
